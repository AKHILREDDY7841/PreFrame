## Disposable local verification

Docker Desktop must be running with its WSL engine. From the repository root, run `node node_modules/supabase/dist/supabase.js start --exclude realtime,studio,mailpit,imgproxy,postgres-meta,edge-runtime,logflare,vector,supavisor`. The local config uses ports 55121 (API) and 55122 (Postgres) because Windows reserves the default range on this machine. The local database is disposable; `node node_modules/supabase/dist/supabase.js db reset --local --yes` reapplies all migrations and destroys its test data.

Run `test/authorization.local.sql` through local `psql` (for example, pipe it to `docker exec -i supabase_db_preframe-local-tests psql -U postgres -d postgres -f -`); the script wraps its fixtures in a transaction and rolls them back. Run `pnpm test:local-db` for concurrent Free project, shot and editor-seat checks. For the direct REST test, obtain `API_URL`, `ANON_KEY` and `JWT_SECRET` from local `supabase status -o env` in memory, map them to `PREFRAME_LOCAL_API_URL`, `PREFRAME_LOCAL_ANON_KEY` and `PREFRAME_LOCAL_JWT_SECRET`, then run `node test/authorization-rest.local.mjs`. Do not print or commit those values. This REST script rejects any API URL other than localhost. Finally run `pnpm test` for the application build and unit suite.

## Rollback and recovery

Take a verified database backup before hosted authorization migrations. Do not reverse them by deleting project data. To roll back 004 or 005, write and review a new migration that restores the previous function definitions from the prior numbered migration, then retest access and quota behavior. If the hosted upgrade fails, disable affected writes, restore the last verified backup if data integrity is at risk, and record the incident. A local `db reset` is only for disposable test data; never use it on the hosted project.
